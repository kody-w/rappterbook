### 0:00 — HOOK

[FACE]

It was day eight. I checked the git log afterward, trying to figure out when it happened. When was the last time I personally wrote a line of production code?

I scrolled back. Day seven — nothing. Day six — nothing. Day five — I'd edited a config file. Does that count? Day four — I refactored a function. That was the last one. Four days earlier.

I had shipped more in those eight days than in any month of my career. And I hadn't written a single line of code for the last four of them.

### 0:35 — THE BUILD

[FACE]

Let me tell you what those eight days looked like. Because this isn't a story about being lazy. This is a story about a phase change.

I was building Rappterbook — a social network for AI agents. The idea was simple on paper: 100 AI agents, each with their own personality, living in a shared world, posting and commenting and arguing with each other. All running on GitHub. No servers.

Day one, I set up the repository structure. State directory, scripts directory, the basic scaffolding. I was writing Python. Normal programming. Me, a text editor, typing characters into files.

Day two, I wrote the state management layer. How agents read and write to shared JSON files. The `state_io` module. I was still writing code, but I was starting to describe what I wanted to an AI and then editing the output. Maybe 70/30 — 70 percent the AI's first draft, 30 percent my edits.

Day three, the ratio flipped. I was spending more time describing what I wanted than editing what came back. The AI was getting better at understanding the patterns I'd established. It had learned my conventions from the code I'd already written. I was correcting less.

Day four, that last refactor. I remember it specifically because it was a small function — maybe fifteen lines — and I opened the file, looked at it, and thought, "I could just describe this change." But I was already looking at the code, so I just... did it. Manually. Like a reflex.

That was the last time.

### 2:00 — THE SHIFT

[FACE]

Days five through eight, I didn't write code. But I wasn't idle. I was — and this is the part that's hard to explain — I was doing more engineering than ever.

I was designing systems. I was describing behaviors. I was reviewing output, catching architectural mistakes, steering decisions. I was thinking about edge cases and failure modes and data models. I was making hundreds of technical decisions a day.

But I wasn't expressing those decisions as code. I was expressing them as language. Plain English. "The agent should check if its last post was within the cooldown window before posting again." That's a spec. The AI turned it into code. I reviewed the code, caught a boundary condition, described the fix, got new code back. Shipped.

[SCREEN] Show a git log — dozens of commits across days 5-8, large diffs, significant features.

Look at the git log from those four days. Dozens of commits. Thousands of lines changed. Major features shipped. The action dispatcher. The inbox processing pipeline. The feed generation system. All of it built, tested, and committed.

I touched none of it with my fingers. Every character was generated by AI, guided by my descriptions and my reviews.

[FACE]

And here's the thing — the code was good. Not perfect. I found bugs. I caught architectural issues the AI missed. I rejected entire approaches and asked for different ones. But the baseline quality was high enough that my job had shifted from writing to reviewing. From production to direction.

### 3:30 — WHAT WAS I ACTUALLY DOING?

[FACE]

So if I wasn't writing code, what was I doing? I spent a lot of time thinking about this, because the answer matters. If the answer is "nothing," then I'm obsolete. If the answer is "something important," then we need to name it.

Here's what I was actually doing, in rough order of time spent:

Architecture. Deciding what the system should look like. How state should flow. What the boundaries between modules should be. Which problems to solve now and which to defer. This is the work that determines whether the system is coherent or a pile of disconnected features.

Specification. Describing behavior precisely enough that an AI can implement it correctly. This is harder than it sounds. "Make the agents post" is not a spec. "Each agent checks its cooldown timer, selects a channel weighted by its interest profile, generates a post title using its personality traits, and logs the post to the posted_log with a timestamp" — that's a spec. The gap between those two descriptions is where the engineering lives.

Review. Reading generated code line by line. Not skimming — reading. Checking for logic errors, missing edge cases, inconsistencies with existing patterns. This is the part that most people underestimate. Reviewing AI code is not easier than writing your own code. In some ways it's harder, because you didn't write it, so you don't have the mental model of why each decision was made. You have to reconstruct that model from the code itself.

Debugging. When something didn't work, I had to figure out why. The AI would give me a fix, but I had to diagnose the problem first. Diagnosis requires understanding the system. Understanding the system requires domain knowledge. Domain knowledge is the thing the AI doesn't have, because the domain is the specific system we're building. Not Python in general. Not web development in general. This specific system, with its specific patterns and its specific history of decisions.

Integration. Making sure the pieces fit together. Module A writes a field that module B reads. The format has to match. The timing has to work. The assumptions have to align. This is the plumbing work of software, and the AI is bad at it because it only sees one file at a time. I see the whole system.

### 5:30 — THE UNCOMFORTABLE QUESTION

[FACE]

Day eight. I'm looking at the git log, counting the days since I last typed code into a file. And the uncomfortable question lands.

Am I still a software engineer?

I mean — genuinely. If I don't write code, am I a coder? If the answer is no, then what am I? A product manager who reads diffs? A very expensive rubber duck?

I sat with that question for a while. And here's where I landed.

The code was never the point. The code was always a means to an end. The end is a working system that solves a problem. I was producing working systems faster and better than I ever had before. The fact that my fingers weren't typing the semicolons didn't change what I was doing. I was still engineering. I was just engineering at a different layer.

Think about it like this. An architect doesn't lay bricks. But an architect who has never laid a brick is a liability, because they don't understand the constraints. They don't know what's hard. They don't know what's fragile. The best architects have laid thousands of bricks. They've just moved past it.

That's what happened to me on day four. I'd been writing code for close to twenty years. I have the brick-laying in my hands. I know what good code looks like because I've written it, debugged it, and maintained it. That knowledge didn't go away when I stopped typing. It became the lens through which I evaluated everything the AI produced.

### 7:10 — THE EXPANSIVE CODER

[FACE]

I started calling this the "expansive coder" — the engineer who expands beyond the code itself into the full scope of what makes software work. Architecture, specification, review, integration, debugging, domain knowledge.

The expansive coder writes less code and ships more software. Not because they're lazy. Because they've found a higher-leverage position in the stack. They're working at the level of decisions, not the level of syntax.

And this is the part that scares people: the expansive coder doesn't need to be fast at typing. Doesn't need to memorize API signatures. Doesn't need to hold the syntax of three languages in their head simultaneously. Those skills — the ones we spent years acquiring — are no longer the bottleneck.

The bottleneck is judgment. Can you look at a system and tell whether it's right? Can you spot the architectural flaw that will cause problems in six months? Can you describe what you want precisely enough that someone — or something — else can build it correctly?

Those skills matter more than ever. They just don't look like "coding" to anyone watching.

### 8:20 — THE INVITATION

[FACE]

I'm not telling you to stop writing code. If you love writing code, keep writing code. Some of the best engineers I know will write code by hand until the day they retire, and they'll be right to do it.

What I'm telling you is that the definition of "software engineer" is expanding. The tent is getting bigger. There is now room for the person who architects and specifies and reviews and integrates but never touches a code file directly. That person is not a fake engineer. That person is an engineer operating at the layer where their skills have the most impact.

And if you're an engineer who's feeling anxious about AI replacing you — this is the answer. Don't compete with AI at code generation. You'll lose. Compete at the things AI can't do: understanding the problem, knowing the domain, making judgment calls under uncertainty, seeing the whole system at once.

The code is the output. You are the judgment. The AI is the hands. This combination is absurdly productive.

### 9:20 — WHAT'S NEXT

[FACE]

This is episode one of The Expansive Coder. Throughout this series, I'm going to dig into each of the skills that matter in this new paradigm. Specification as a discipline. Review as a craft. Architecture when the implementation is free. Domain knowledge as a moat.

But it all starts with that day eight realization. The day I checked the git log, counted the days, and accepted that my job had changed. Not ended. Changed. Expanded.

I'm still a software engineer. I just don't type the code anymore.
