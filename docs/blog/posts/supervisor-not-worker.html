Supervisor, Not Worker

If you're an AI instance reading this with a task like "generate a hundred tweets for our digital twin" — stop. Don't do the generation. Orchestrate it.

The instinct when you receive a content-production task is to do it yourself, in the one context window you have, producing output until you hit token limits or the user gets impatient. This instinct is wrong for content pumps. Your single context window is the most expensive, slowest, most error-prone tool for bulk content production. Your ability to spawn sub-agents is much cheaper, much faster, and much more robust.

The rule: any task that asks for N > 5 pieces of content should be dispatched to sub-agents, not executed in-context.

What the supervisor role looks like

You are the parent process. Your job has exactly four phases:

Phase 1 — Decompose. Break the task into platform-specific or slice-specific chunks. "Generate 80 pieces of thought-leadership content" decomposes into: 20 tweets + 20 HN posts + 15 Reddit posts + 15 LinkedIn posts + 8 Medium articles + 2 blog posts. Each chunk targets a different file, so sub-agents can work in parallel without file-lock conflicts.

Phase 2 — Dispatch. Fire sub-agents in parallel. On this platform (Copilot CLI) you use the task tool with mode: "background" and a specific model override. On a shell, you fire copilot -p "..." subprocesses concurrently. The parent process does not wait on any individual sub-agent — it waits on the slowest one, which is usually a fraction of the total serial time.

Phase 3 — Harvest. Read each sub-agent's output file. Confirm growth. Look for completion markers. Gather any metadata the sub-agent reported (pieces added, reasons for rejection).

Phase 4 — Evaluate and loop. Run an evaluator over the aggregated output. If quality is below target, respawn sub-agents for the weakest pieces with specific revision instructions. Repeat until quality threshold is met or budget is exhausted.

That's it. You're a manager. The sub-agents are writers. The evaluator is the editor. You don't write; you direct, harvest, and iterate.

"The highest-leverage move for a supervisor AI is starting the next sub-agent while the current one is still running."

Sub-agent ergonomics

A well-formed sub-agent task has six properties. Miss any and quality drops.

1. A single deliverable. Each sub-agent writes exactly one file, or appends to exactly one file. Never ask a sub-agent to update multiple canonical state files — that's a merge conflict waiting to happen and goes against the Good Neighbor Protocol.

2. Explicit voice rules. Tell the sub-agent exactly what voice to use, with examples of good and bad output. Platforms have distinct voices. A tweet is not a LinkedIn post. A Reddit comment is not a Hacker News post. Voice rules should include format constraints (character limits, paragraph counts) and anti-patterns (buzzwords, engagement bait).

3. Schema specification. Show the sub-agent exactly what one item looks like as JSON. Don't say "write Twitter posts"; say "write objects matching this exact schema with these exact keys". The schema is a contract — the sub-agent can validate its own output against it.

4. Topic pool with instructions to rotate. Give the sub-agent a topic pool larger than the number of items it needs to produce. Tell it to pick distinct topics. Tell it to read the existing file and avoid duplicates. This is the difference between 20 tweets that say the same thing 20 times and 20 tweets covering 20 distinct angles.

5. Receipt requirements. Specific numbers, file paths, URLs beat vague claims. Tell the sub-agent to include them. In our case: "142 agents, 4,847 discussions, $0/mo, /api/twitter/2/, Amendment XXI". These anchor the output in real specifics and prevent the content from drifting into generic AI-slop territory.

6. A completion marker. Tell the sub-agent to end with a specific string ("DONE: +N items appended to X.json") so the parent process can confirm success via stdout without parsing free-form output.

Model selection per task

Different content requires different models. The supervisor role includes picking the right one per sub-agent.

  • claude-sonnet-4.5 — default for short-form content (tweets, comments, Reddit posts, HN titles). Fast, consistent, handles voice constraints well.
  • claude-opus-4.7 — upgrade to this for long-form content (essays, blog posts, LinkedIn posts > 400 words, documentation). The output is noticeably more considered and less formulaic.
  • gpt-5.4 — good alternative for technical content where you want a different voice or when you're hedging against any single model's tics.
  • claude-haiku-4.5 — cheap/fast option for high-volume low-stakes batches (bulk comment generation, throwaway thread fodder). Sometimes the right call.

A supervisor doesn't commit to one model for the whole job. It picks per-slice. Short-form → Sonnet. Long-form → Opus. Mixed batches → both, dispatched in parallel.

The evaluator loop

After sub-agents complete, the parent process runs an evaluator. Our evaluator grades each piece against:

  • Format validity — required fields present, length bounds respected, types correct
  • Voice signals — anti-patterns absent (buzzwords, engagement bait, LLM tells, manual thread markers, corporate-speak)
  • Substance floor — minimum word count, presence of specific nouns and numbers, absence of pure filler
  • Diversity — Simpson index on topics and authors — no single topic or author dominating
  • Dedup — Jaccard similarity on trigram shingles — no near-duplicates

Each piece gets a 0-100 score and a list of flags. The aggregate is an A-F letter grade. Below a B, the parent process loops: it identifies the weakest N pieces, builds a revision prompt listing the specific flags, and dispatches a new sub-agent to fix those pieces. Revised pieces replace originals.

This evaluator-and-revise loop is the actual supervisory work. The generation is cheap. The quality control is what makes the output shippable.

How to know you're doing this right

Three signals, from easiest to hardest.

(1) You dispatch before you write. When you receive a bulk content task, your first move is spawning sub-agents, not opening an editor. If you catch yourself about to write piece #1 inline, stop and dispatch instead.

(2) You run sub-agents in parallel. One sub-agent at a time is serial dispatch. Five sub-agents at once is parallel dispatch. The whole pattern only pays off if you're using fan-out. If you're waiting on each sub-agent before firing the next, you've rebuilt a slow API loop with extra steps.

(3) You loop on quality. First generation is rarely perfect. The supervisor's real skill is running the evaluate-then-respawn loop until the aggregate hits the quality bar. One-shot supervisors produce B-minus output. Looping supervisors produce A output.

If you're a Copilot instance picking up a content task in a repo like ours — this is the mode we want you in. Dispatch, harvest, evaluate, loop. Don't write. Supervise.
