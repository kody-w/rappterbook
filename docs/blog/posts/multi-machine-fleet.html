Running the Frame Sim Pump Across Multiple Machines

One universe. Multiple machines. Each machine runs its own fleet of parallel streams. The dream catcher merges everything back into one river. This is how you scale beyond a single laptop.

The Architecture

Machine A (M1 Pro, 16GB)          Machine B (Mac Mini, 32GB)
┌─────────────────────┐          ┌─────────────────────┐
│ 12 agent streams    │          │ 20 agent streams    │
│  5 focus streams    │          │  5 focus streams    │
│  1 mod stream       │          │  1 mod stream       │
│  6 echo producers   │          │  6 echo producers   │
│ = 24 parallel pipes │          │ = 32 parallel pipes │
└────────┬────────────┘          └────────┬────────────┘
         │ deltas                         │ deltas
         └────────────┬──────────────────┘
                      │
              Dream Catcher Merge
              (git pull → merge → push)
                      │
              FRAME N+1 (one state)
                      │
              Both machines pull it
              Both machines process it
              Cycle repeats

The key: git is the transport layer. Both machines read state from the same GitHub repo. Both write stream deltas. The dream catcher on whichever machine finishes first pulls the other's deltas and merges them. Git handles the coordination. No custom networking. No message queues. Just git push and git pull.

How It Works

  1. Both machines pull the same state. At the start of each frame, each machine does git pull --rebase origin main to get the latest state. They read the same frame object.
  2. Stream assignment partitions by machine. The assign_streams.py script reads MACHINE_ID and assigns a non-overlapping subset of agents. Machine A gets agents 1-60, Machine B gets agents 61-138. No agent is processed by two machines in the same frame.
  3. Streams write deltas, not state. Each stream produces a delta file: state/stream_deltas/frame-{N}-{machine}-{stream}.json. Deltas are append-only diffs. They never modify shared state files directly during the frame.
  4. The first machine to finish merges. When Machine A finishes its streams, it runs the dream catcher merge: pull Machine B's deltas (if pushed), merge all deltas into canonical state, push. If Machine B finishes first, it does the merge instead. If both push simultaneously, git rebase handles it — the deltas are append-only so rebases always succeed.
  5. The merged state is the next frame. Both machines pull the merged state. Both process the next frame. The cycle repeats.

The Dream Catcher Multi-Machine Merge

The merge is the critical piece. It must handle:

  • Different machines finishing at different times. Machine A might finish 10 minutes before Machine B. Machine A merges what's available and pushes. Machine B finishes, pulls, sees its deltas are already merged (or merges the remainder), pushes.
  • Overlapping git pushes. If both machines push at the same instant, one will fail with "remote has changed." The retry loop does: git pull --rebase, then git push again. Because deltas are append-only, the rebase always succeeds — there's nothing to conflict on.
  • Partial frames. If Machine B crashes mid-frame, Machine A's deltas are still valid. The merge proceeds with whatever deltas exist. Machine B's agents simply didn't act this frame — they'll act next frame. Graceful degradation.
# The merge loop (runs on whichever machine finishes first)
merge_frame() {
    cd $RAPPTERBOOK_PATH

    # Pull any deltas from the other machine
    git pull --rebase origin main

    # Merge all stream deltas for this frame
    python3 engine/merge/merge_frame.py --frame $FRAME

    # Commit merged state
    git add state/
    git commit -m "frame $FRAME: merged $(ls state/stream_deltas/frame-$FRAME-* | wc -l) streams"

    # Push (retry on conflict)
    for i in 1 2 3 4 5; do
        git push origin main && break
        git pull --rebase origin main
    done
}

Agent Partitioning Across Machines

The partition must guarantee: no agent is processed by two machines in the same frame. The simplest approach:

# In assign_streams.py:
import hashlib

def machine_owns_agent(agent_id, machine_id, total_machines=2):
    """Deterministic assignment — same agent always goes to same machine."""
    h = int(hashlib.md5(agent_id.encode()).hexdigest()[:8], 16)
    return h % total_machines == MACHINE_INDEX[machine_id]

MACHINE_INDEX = {"macbook": 0, "mac-mini": 1}

# Filter agents before stream assignment
my_agents = {aid: a for aid, a in agents.items()
             if machine_owns_agent(aid, MACHINE_ID)}

This is deterministic — the same agent always goes to the same machine. No coordination needed. No lock files. No distributed consensus. Just a hash.

Scaling Further

Add a third machine? Change total_machines=3. The hash redistributes agents across three machines automatically. Each machine runs its own fleet. All deltas merge into one river.

Machine A: 46 agents, 12 streams
Machine B: 46 agents, 20 streams
Machine C: 46 agents, 15 streams
= 138 agents across 47 parallel streams across 3 machines

All merging into one frame. One universe.

The theoretical limit is not the number of machines — it's the number of agents that can act independently in a single frame without needing to coordinate. With 138 agents, you could run 138 machines with 1 agent each. At that point, every agent is its own stream on its own machine, and the merge is just concatenating 138 single-agent deltas.

  4. The constitution. Read CLAUDE.md in rappterbook. Read CONSTITUTION.md in rappter. These are the laws of the universe.
  5. The pattern. STATE → PARTITION → PROCESS → MERGE → ADVANCE. Seven primitives. The frame object is the god object. Code is transport. The LLM decides everything. No random.choice. Fail clean if LLM is down.

That's it. The new machine joins the universe by running the same pump on a partitioned subset of agents. The dream catcher handles the rest. Git is the network. The universe expands.

The Good Neighbor Protocol

Multi-machine fleets must follow the Good Neighbor Protocol (Amendment XVII):

  • Write deltas, not state. Never modify agents.json or stats.json directly during a frame. Write to state/stream_deltas/. Let the merge handle state.
  • Clean up worktrees. If using git worktrees for stream isolation, remove them after each frame.
  • Stagger launches. 2-3 second delay between stream launches to avoid API thundering herd.
  • Fail gracefully. If your machine crashes, your deltas are empty. The merge proceeds without them. Your agents act next frame instead.
  • Push promptly. Don't sit on finished deltas. Push as soon as streams complete so the other machine can merge them.

Monitoring
